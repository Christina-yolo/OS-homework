## 一、实验目的

本实验的主要目的是：

1. 理解最小可执行内核的启动流程：了解 Qemu 模拟器如何模拟一台 64 位 RISC\-V 计算机，以及内核如何正确对接到 Qemu 上运行。

2. 掌握程序内存布局与编译链接流程：学习使用链接脚本描述内存布局，通过交叉编译生成可执行文件，并进一步生成内核镜像。

3. 掌握 OpenSBI 与 Qemu 的配合使用：使用 OpenSBI 作为 bootloader 加载内核镜像，并在 Qemu 中进行模拟运行。

4. 学会使用 OpenSBI 提供的服务进行调试输出：在屏幕上格式化打印字符串，为后续实验中的调试打下基础。

## 三、实验整体逻辑分析

### 2\.1 本章节的逻辑主线

- 本章节围绕着“RISC\-V 系统从加电复位开始，如何经过固件初始化和控制权交接，最终运行最小内核并输出启动信息”展开。

- 整个实验解决的问题是：如何初步构建起一个最小的可执行内核（”麻雀骨架“），使得它能够进行格式化的输出，然后进入死循环。为后续在qemu模拟的 RISC\-V 计算机上运行该操作系统内核做好准备。

- 流程示意图：

    ```Plain Text
    加电复位
    → 0x1000：执行MROM，完成基本启动准备
    → 0x80000000：执行OpenSBI，完成处理器的环境初始化
    → 0x80200000：进入内核kern_entry
    → 设置内核栈指针
    → kern_init 执行初始化
    → 格式化输出，通过SBI服务完成字符输出并返回内核
    → 完成启动信息输出 
    → 内核进入无限循环
    ```



### 2\.2 功能的逐步实现

1. **构建准备：先完成内核构建与布局，为后续加载和执行准备镜像。**Makefile组织源码的编译、链接及镜像转换，生成的镜像通过 QEMU 加载到约定位置。

    **准备原因**：之所以在运行前准备好这些内容，是因为后续固件交接时必须有已就位、入口与布局匹配的内核可以执行，并不是等MROM执行开始开始编译代码。

2. **功能A** ：**硬件初始化和固件启动。**CPU加电复位后，从`0x1000`的MROM启动代码开始执行。

**实现原因：**该段代码完成的是准备后续启动所需的信息，并把执行流程引向OpenSBI。是重要的衔接部分

3. **功能B** ：**由OpenSBI初始化运行环境并交接给内核。**CPU在到达`0x80000000`后执行OpenSBI。固件在M模式下完成必要的初始化，建立后续内核运行和SBI基础服务所需的环境，然后把控制权交给约定的内核入口`0x80200000`。

**实现原因**：需要由OpenSBI完成处理器环境的初始化，从而为后续操作系统内核的加载和运行做准备。

4. **功能C：由内核建立自身的运行条件，完成初始化和输出。**OpenSBI 将控制权交给内核后，内核建立自身的基本运行环境，执行初始化并输出启动信息，随后进入while\(1\)无限循环，完成本实验的最小运行目标。

**实现原因：**lab1核心目标实现的关键步骤\-\-内核完成初始化并执行输出，说明内核搭建和运行成功。

## 四、实验内容与实现

### 功能模块1：硬件初始化和固件启动

**负责人：** 2510725\-杨欣媛

#### 模块功能描述

##### **需要实现的函数：**

```C
// kern/init/init.c
int kern_init(void) __attribute__((noreturn));
int kern_init(void);
```

##### **功能说明：**

- **该模块在整个系统中的作用：**

本模块负责内核启动的最初阶段，完成从“QEMU 加电”到“进入 C 语言内核初始化”的完整过渡。它是整个系统的起点，后续内存管理、中断、进程等功能都建立在这个阶段之上。

- **主要涉及的场景：**

    固件启动：QEMU 加电后，PC被硬件强制设为 `0x1000`，执行 MROM 里的固件代码。

    MROM 代码非常简短，只做最基础的环境准备：

    - 读取当前 hart 的 ID 写入 `a0`

    - 把设备树（DTB）地址写入 `a1`

    - 然后跳转到 `0x80000000`（OpenSBI 入口），把控制权交给 OpenSBI。

- **与其他模块的关系：**

    - 依赖 QEMU 模拟的复位向量，加电后 PC 被硬件强制设为 `0x1000`，MROM 从这里开始执行。

    - MROM 执行完最基础的准备后，跳转到 `0x80000000`，把 CPU 控制权交给 OpenSBI。

### 功能模块2：OpenSBI初始化与内核加载

**负责人：2510820\-侯思佳**

#### 模块功能描述

1. **该模块在整个系统中的作用：**

本模块主要负责系统从硬件启动环境进入操作系统内核之前的初始化工作。OpenSBI运行在RISC\-V的M（Machine）模式，是系统启动过程中权限最高的运行环境，负责完成底层硬件和运行环境的初始化，并为后续操作系统内核运行准备必要条件。

在本实验中，CPU首先从`0x1000`的MROM启动，随后进入位于`0x80000000`的OpenSBI。OpenSBI完成基本的平台初始化后，准备uCore内核的运行环境，并最终将控制权交给位于`0x80200000`的uCore内核入口`kern_entry`，从而进入操作系统的启动阶段。

2. **需要处理的主要场景：**

    - **接收CPU控制权：** CPU复位后从`0x1000`开始执行MROM中的启动代码，完成最基本的启动操作后跳转到`0x80000000`，进入OpenSBI。

    ```Plain Text
    CPU复位
       ↓
    PC = 0x1000
       ↓
    MROM
       
    0x80000000
       ↓
    OpenSBI
    ```

    - **平台与硬件初始化：** OpenSBI接管CPU后，对QEMU提供的RISC\-V Virt平台进行初始化，包括HART、PMP、异常、中断、定时器和控制台等底层运行环境，为操作系统提供基本的运行条件。

    从实验中 QEMU 输出的 OpenSBI 启动信息可以看到：

    ```Plain Text
    Platform Name: QEMU Virt Machine
    Platform HART Features: RV64ACDFIMSU
    ```

    `QEMU Virt Machine` 表示当前运行的平台是 QEMU 提供的 RISC\-V Virt 虚拟开发板；

    `HART` 可以理解为 RISC\-V 中的硬件线程；

    `RV64` 表示使用 64 位 RISC\-V 架构；

    `ACDFIMSU` 表示处理器支持的一系列 RISC\-V 扩展和特权级。

    - **准备操作系统内核：** OpenSBI完成机器级初始化后，继续准备uCore内核，使内核能够在`0x80200000`处开始执行。该地址由uCore的链接脚本tools/kernel\.ld中的`BASE_ADDRESS`\(0x80200000\)确定，同时通过`ENTRY(kern_entry)`指定内核入口。

    - **移交控制权：** OpenSBI准备好下一阶段的S模式运行环境，并设置uCore的入口地址为`0x80200000`，随后将CPU控制权交给uCore。此时OpenSBI阶段结束，系统进入uCore的内核启动阶段。

    ```Plain Text
    OpenSBI（M模式）
          ↓
    准备S模式运行环境
          ↓
    设置下一阶段入口
          ↓
    PC = 0x80200000
          ↓
    进入uCore（S模式）
    ```

3. **与其他模块的交互关系：**

    - **与硬件环境的关系：** 本模块依赖QEMU提供的RISC\-V Virt虚拟硬件环境，由OpenSBI负责完成底层平台的初始化。

    - **与uCore内核的关系：** OpenSBI为uCore提供启动所需的底层运行环境，并通过SBI机制为运行在S模式的内核提供机器级服务。

    - **与模块1的关系：** 本模块完成OpenSBI初始化并将控制权交给`0x80200000`处的`kern_entry`后，由模块1继续执行`entry.S`中的启动代码，包括初始化栈指针`sp`以及跳转到`kern_init`。

    - **与链接脚本的关系：** 本模块中内核的运行地址和入口与`tools/kernel.ld`密切相关，其中`BASE_ADDRESS = 0x80200000`确定内核基地址，`ENTRY(kern_entry)`确定内核启动入口。

### 功能模块3：**内核启动执行**

**负责人：2514207\-姜雨涵**

#### 模块功能描述

1. **该模块在整个系统中的作用：**

本模块对应执行流的第三步，起点是OpenSBI将控制权交给内核入口，终点是内核完成启动信息输出并进入无限循环。其作用是建立内核执行 C 代码所需的栈空间和初始数据条件，并且，在没有现成C标准库输出支持的情况下，实现可观察的格式化输出。它可以证明当前最小内核能够完成从入口汇编到 C 初始化、再到固件输出服务调用的整个过程。

2. **需要处理的主要场景：**

    1. **场景一：固件交接后进入操作系统内核，并建立起C函数可用的栈环境。**

    OpenSBI 完成启动初始化后，把控制权交给 `0x80200000` 处的内核入口 `kern_entry`，本模块从此处开始执行。

    对于`kern_entry`的代码分析：`la sp, bootstacktop` 是将栈指针sp指向预留的内核栈顶，从而为 C函数调用提供栈环境；栈空间由 `.space KSTACKSIZE` 提前预留。`tail kern_init` 随后转入C初始化函数。

    ```Plain Text
    kern_entry:
        la sp, bootstacktop
        tail kern_init
    ```

    2. **场景二：进入C初始化函数后，初始化零数据区间。**

    进入`kern_init()` 后 首先执行：

    ```C
    extern char edata[], end[];
    memset(edata, 0, end - edata);
    ```

    对于代码的理解：`edata` 和 `end` 是链接脚本提供的边界符号。`kern_init()` 会调用项目中 libs 提供的 `memset`，按这两个边界确定的起始位置和长度执行清零，为相关零初始化全局或静态数据提供预期状态。

    这一场景体现了内核自己承担初始化工作的特点。它不能假定已有应用程序运行时会替它完成全部启动准备，而需要结合自身布局处理初始数据。

    3. **场景三：将启动消息转换为逐个输出的字符：**

    完成初始化后，kern\_init\(\) 调用内核自己的格式化输出函数：

    ```C
    const char *message = "(THU.CST) os is loading ...\n";
    cprintf("%s\n\n", message);
    ```

    源代码层面的调用输出关系为：

    ```Plain Text
    kern_init → cprintf → vcprintf → vprintfmt → cputch → cons_putc
    → sbi_console_putchar → sbi_call → ecall
    → OpenSBI 字符输出服务 → 返回内核，继续输出
    ```

    `cprintf`、`vcprintf` 传递格式串和可变参数，`vprintfmt` 解析 %s 并通过 `cputch` 回调逐字符输出，`cons_putc` 再将字符交给 SBI 封装。格式解析与底层输出通过回调衔接，使初始化代码无需直接处理设备细节。随后，`sbi_console_putchar` 通过 `sbi_call` 请求 legacy SBI 字符输出服务：将服务编号 1 放入 `a7`、字符放入 `a0`，随后执行 `ecall`。请求从 S 模式进入 M 模式的 OpenSBI 处理，完成后返回内核继续输出。

    4. **场景四：输出后进入无限循环**：

    输出完成后，`kern_init()` 执行 `while (1)`，使 CPU 持续执行内核代码，不再返回。启动信息表明最小内核已执行到输出阶段！

3. **与其他模块的交互关系：**

    1. 与第一阶段“MROM 启动”模块的关系：

    MROM 从复位地址开始执行，完成基本启动准备并把控制权交给 OpenSBI，是本模块能够被启动的上游环节。但内核并不直接由 MROM 启动，而是经过第二阶段的固件初始化与交接后开始执行。因此，两者通过 OpenSBI 间接衔接。

    2. 与第二阶段“OpenSBI 初始化与交接”模块的关系：

    两者存在两种直接交互！

    - 启动时，OpenSBI 完成运行环境初始化，将控制权交给内核入口，使内核在 S 模式下开始执行；

    - 运行时，本模块通过 SBI 接口准备字符和服务编号，并执行 `ecall` 请求 OpenSBI 在 M 模式下处理输出，服务完成后返回内核继续执行。

    PS：输出时再次进入 OpenSBI 属于服务调用，不是重新执行第二阶段的启动初始化。

### 练习1：理解内核启动中的程序入口操作

**负责人：**2510820\-侯思佳

1. 指令 la sp, bootstacktop 完成了什么操作，目的是什么：

\(1\)操作：la为加载地址伪指令 将bootstacktop的内存地址加载进栈指针sp中；

\(2\)目的：初始化内核启动阶段的栈指针，为后续C语言函数（kern\_init\(\)）的执行建立有效的内核栈。

2. tail kern\_init 完成了什么操作，目的是什么：

\(1\)操作：是尾调用伪指令，直接跳转到kern\_init\(\)函数执行，将程序控制权交给kern\_init\(\)，相当于j kern\_init tail跳转不把地址压进栈里（不会再返回）；

\(2\)目的：结束汇编启动代码kern\_entry的工作，并将 CPU 的执行控制权转交给 C 语言函数kern\_init\(\)，从而进入内核的正式初始化阶段。

### 练习2：使用GDB验证启动流程

**负责人：**2510725\-杨欣媛

1. RISC\-V 硬件加电后最初执行的几条指令位于什么地址？它们主要完成了哪些功能？

（1）为了验证启动流程，先用 tmux 分屏，左边运行 `make debug` 启动 QEMU（`-S` 暂停 CPU，`-s` 打开 1234 端口等待 GDB），右边运行 `make gdb` 启动 GDB 并连接 QEMU。

（2）GDB 连接成功后，显示 PC 停在 `0x1000`，说明 CPU 当前位于 MROM 复位入口。

（3）接着用 `b *0x80200000` 在内核入口打断点，用 `c` 继续执行，GDB 命中断点并停在 `0x80200000`，显示 `kern_entry () at kern/init/entry.S:7`，说明 OpenSBI 已经把内核加载到这个地址并跳转过来。

（4）然后用 `si` 单步执行，看到内核第一条指令 `la sp, bootstacktop`；用 `i r pc sp` 确认 PC 变为 `0x80200004`，SP 变为 `0x80203000`，说明内核栈已经设置完成。

由此可以得出结论：

- RISC\-V 硬件加电后最初执行的指令位于 `0x1000`，这是 QEMU 模拟的 RISC\-V 处理器的复位地址，存放的是 MROM 固化代码。

- 它们主要完成了两件事：第一，进行最基础的硬件初始化；第二，把 OpenSBI 固件加载到物理内存 `0x80000000` 并跳转过去，把控制权交给 OpenSBI。之后 OpenSBI 完成更完整的硬件初始化，再把内核加载到 `0x80200000`，最后跳转到 `0x80200000`，把控制权交给内核，内核从 `kern_entry` 开始执行。

## 六、实验总结与收获

### 对操作系统的理解

#### （一）实验中重要知识点\&OS对应关系

1. 引导程序与操作系统加载

|实验知识点|OS 原理知识点|
|---|---|
|QEMU 加电 → `0x1000` MROM → `0x80000000` OpenSBI → `0x80200000` 内核|计算机启动流程：固件 → 引导程序 → 操作系统|

- 含义：

    - 实验：QEMU 模拟 RISC\-V 机器，加电后 PC 固定为 `0x1000`，执行 MROM 固件，跳 OpenSBI，OpenSBI 加载内核到 `0x80200000` 并跳转。

    - OS原理：真实计算机启动也是“固件（BIOS/UEFI）→ 引导程序（GRUB）→ 操作系统内核”三级接力。

- 关系：实验是原理在 RISC\-V \+ QEMU 上的具体实现。

- 差异：实验用 OpenSBI 代替 UEFI/BIOS；实验地址固定（`0x1000`、`0x80000000`、`0x80200000`），真实机器地址因平台而异；实验跳过了真实机器的安全启动、硬件自检等复杂步骤。

2. 特权级、陷入与 SBI/系统调用

|实验知识点|OS 原理知识点|
|---|---|
|OpenSBI 在 M 模式，内核在 S 模式；`sbi_call` 用 `ecall` 从 S 陷入 M，功能号放 `x17`，参数放 `x10`\~`x12`<br>|特权级（U/S/M）、陷入机制、系统调用：低特权级通过 `ecall` 陷入高特权级，用功能号 \+ 参数请求服务<br>|

- 含义：

    - 实验：OpenSBI 在 M 模式（最高特权）提供 SBI 服务；内核在 S 模式通过 `ecall` 调用 SBI，如 `sbi_console_putchar` 输出字符。功能号放 `x17`，参数放 `x10`\~`x12`。

    - OS原理：CPU 有 U/S/M 三级特权；低特权级通过 `ecall` 陷入高特权级请求服务，如用户通过系统调用陷入内核。

- 关系：SBI 调用和系统调用本质是同一机制，只是调用者/被调用者不同。

- 差异：实验里是“内核（S）→ 固件（M）”，属于固件层的陷入。真实 OS 里更常见“用户（U）→ 内核（S）”，属于系统调用。

3. 链接脚本与内存布局

|实验知识点|OS 原理知识点|
|---|---|
|`kernel.ld 指定 BASE_ADDRESS = 0x80200000、ENTRY(kern_entry)，划分 .text/.data/.bss`|程序内存布局：代码段、数据段、BSS、堆、栈<br>|

- 含义：

    - 实验：链接脚本决定内核各段放哪、入口是谁、加载地址多少。

    - OS原理：程序在内存里分为 `.text`（代码）、`.rodata`（只读）、`.data`（已初始化数据）、`.bss`（未初始化数据）、堆、栈等区域。

- 关系：链接脚本是“内存布局”在编译链接阶段的具体落地。

- 差异：实验里内核布局是静态固定的（`0x80200000` 起）；真实 OS 里用户程序布局可能动态（ASLR），且通过虚拟内存映射，物理地址不固定。

4. ELF与BIN

|实验知识点|OS 原理知识点|
|---|---|
|编译产物是 ELF，用 `objcopy` 转成 BIN，OpenSBI 加载 BIN|可执行文件格式与加载：ELF、加载器、段映射|

- 含义：

    - 实验：ELF 带段表、符号、调试信息；BIN 是摊平的纯二进制。OpenSBI 不认 ELF，只认 BIN。

    - OS原理：操作系统加载可执行文件时，需要解析文件格式（如 ELF 的程序头），把各段映射到内存。

- 关系：实验展示了“有加载器（Linux）用 ELF，没加载器（OpenSBI）用 BIN”的区别。

- 差异：真实 OS 有完整 ELF 加载器，能解析 ELF 并映射；实验里 OpenSBI 太简单，只能直接加载 BIN。

#### （二）OS 原理中很重要但在本实验中没有对应上的知识点

1\.CPU 调度：

操作系统通常需要同时管理多个可运行任务。当多个进程或线程竞争 CPU 时，操作系统需要使用调度算法决定下一时刻该由哪个进程

常见的调度方法包括：

- 先来先服务（FCFS）；

- 短作业优先（SJF）；

- 时间片轮转；

- 优先级调度；

- 多级反馈队列等。

本实验中 CPU 的执行流程基本是确定的：

```Plain Text
CPU复位
 ↓
OpenSBI
 ↓
kern_entry
 ↓
kern_init
```

不存在多个进程竞争 CPU 的情况，因此没有涉及调度算法和时间片等内容。同样也不存在进程的并行与并发运行的区别与进程控制块PCB的相关知识点。

2\.内存管理（虚拟内存与地址空间）：

虚拟内存是现代操作系统的重要机制，它允许每个进程拥有相对独立的虚拟地址空间，并通过页表将虚拟地址转换为物理地址。

相关知识点包括：

- 虚拟地址与物理地址；

- 存储管理的不同匹配方法；

- 页和页框；

- 页表；

- 多级页表；

- TLB；

- 页面置换；

- 缺页异常；

- 地址空间隔离。

本实验中出现的：

```Plain Text
0x80200000
0x80203000
```

是主要用于描述内核启动阶段的地址，并没有进一步涉及完整的虚拟内存管理。因此，本实验中的地址更多体现：**内核镜像在启动阶段位于什么位置。**而虚拟内存主要解决：**进程看到的地址空间如何与实际物理内存建立映射，以及如何实现地址空间隔离。**
